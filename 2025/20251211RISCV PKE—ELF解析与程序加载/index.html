    RISCV代理内核实验：系统调用、异常和外部中断（二）ELF解析与程序加载

    背景

    ELF文件结构在ICS的实验中早已接触，这次我们换个视角，谈谈ELF的设计思路。

    试想最简单的汇编程序，翻译成机器码后，就变成了一堆二进制数据，没有结构，符号变成了直接的地址。这样的程序可以直接加载到内存中运行，操作系统只需要把这些二进制数据从磁盘读到内存的某个地址，然后跳转到入口地址即可。程序加载十分友好。

    这种方式非常直接，但存在巨大局限，如果另一个人想要引用其中的模块（函数），他就必须知道这些地址的含义，显然这是一个痛苦的过程，他需要反汇编这个二进制文件，然后推测每条指令的含义，才能找到他想要的函数入口地址。

    就像古代阅读没有标点符号的文章一样，想要阅读理解，得去找先生解读，实在不便。

    又比如，一个程序可能会调用系统接口，如果没有符号信息，鬼知道你在调用什么函数？

    为了管理程序的不同组成部分，出现了像Unix早期的 a.out（汇编器输出）这样的格式。它们引入了最简单的“容器”概念，即一个文件头（可能非常简易），后面跟着几个固定的段，最常见的就是代码段（.text）和数据段（.data）。

    这解决了最基本的分类问题，但格式仍然非常僵化。随着软件规模扩大，需要包含调试信息、支持库的共享（动态链接）等，简单的 a.out格式就力不从心了。

    作为 a.out的改进，通用对象文件格式（COFF） 被引入，例如在System V Release 3中。COFF的关键进步在于引入了更具弹性的“节”（Section） 的概念。一个目标文件可以包含多个节，每个节有自己的名称、类型和属性，并且有一个节头表（Section Header Table） 来描述这些节。
    这使得编译器能够将代码、只读数据、未初始化数据等分别放入不同的节（如 .text, .data, .bss），为链接器提供了更细粒度的控制。COFF还包含了符号表，用于记录函数和变量名及其地址，这是实现多个目标文件链接的基础。

    但COFF的节头数量等仍有限制，扩展性不足以应对日益复杂的软件生态，特别是对动态共享库的优雅支持。

    所以，有必要为程序文件设计一种结构，包含必要的 自我描述信息，方便链接器和操作系统使用，这就是ELF文件格式的初衷。

    ELF的成功源于几个核心设计：

    链接视角：关注的是“节”（Section）。对于编译器和链接器，ELF文件是由节头表（Section Header Table） 描述的一系列节的集合，如 .text（代码）、.data（已初始化数据）、.bss（未初始化数据）、.symtab（符号表）、.strtab（字符串表）等。链接器通过节头表来定位和合并这些节。

    执行视角：关注的是“段”（Segment）。对于操作系统加载器，ELF文件是由程序头表（Program Header Table） 描述的一系列“段”（Segment）的集合。每个段（如类型为 PT_LOAD的段）告诉加载器如何将文件的一部分（通常包含多个属性相同的节，如可读可执行的 .text节和 .rodata节）映射到进程的虚拟地址空间。例如，一个可执行文件通常至少有两个可加载段：一个用于代码和只读数据（权限为 R+X），另一个用于可读写数据（权限为 R+W）。

    总的来说，ELF文件格式通过区分节和段，满足了编译链接和程序加载的不同需求，成为现代操作系统中广泛采用的可执行文件格式。即：

    ELF头 -> 程序头表 -> 段-> 运行时视图
      ↘
节头表 -> 节 -> 链接时视图

    三级指针结构，清晰分工。

    ELF加载程序段

    加载时，我们关注的是ELF的执行视图。整体思路：

    1. 读取ELF头，验证文件格式，获取 程序头表的位置和大小。
    2. 遍历程序头表，找到所有类型为 PT_LOAD的段。
    3. 对于每个 PT_LOAD段，根据其文件偏移和内存地址，将对应的数据从文件读入内存，并设置适当的权限（读、写、执行）。
    4. 设置 堆栈和其他必要的内存区域。
    5. 跳转到 入口点，开始执行程序。

    总结

    通过节头表和程序头表，操作系统能够高效地加载和执行程序，同时链接器也能方便地处理符号和节的合并。这种设计使得ELF成为现代操作系统中广泛采用的可执行文件格式。
    ELF文件格式通过区分节和段，满足了编译链接和程序加载的不同需求。理解ELF的结构和加载过程，对于操作系统开发和调试具有重要意义。

    ELF文件格式设计思路总结

    在计算机科学的早期阶段，程序通常以最简单的形式存在——汇编代码直接翻译成机器码，形成一连串的二进制数据。这种形式的程序虽然可以直接加载到内存中运行，但缺乏结构化的信息，使得程序的管理和扩展变得困难。
    举个例子，假设我们有一个简单的程序，它包含几个函数，每个函数在内存中的地址是硬编码的：

    在这个例子中，程序只是简单地将函数代码按顺序排列在一起，没有任何标识或结构来区分不同的函数。如果我们想要调用 Function B，我们必须知道它在内存中的确切地址，这对于大型程序来说是不可行的。
    此外，程序中可能包含变量和数据，如果没有明确的结构，链接器和加载器将难以正确地处理这些数据。例如，假设程序中有一个全局变量 counter，它在内存中的位置也是硬编码的：

    在这种情况下，链接器无法轻松地将不同的目标文件合并在一起，因为它们可能会有冲突的地址空间。加载器也无法正确地将数据和代码映射到内存中，因为它缺乏必要的元信息。

    为了解决这些问题，程序文件格式逐渐演变出更复杂的结构，包含必要的元信息，以便链接器和加载器能够正确地处理程序。最早的目标文件格式之一是 a.out，它引入了一些基本的结构，如代码段和数据段，但仍然存在许多限制。
    随后，COFF（Common Object File Format）被引入，提供了更丰富的结构化信息。COFF 文件格式引入了节（Section）的概念，每个节包含特定类型的数据或代码。例如，.text 节包含代码，.data 节包含已初始化的数据，.bss 节包含未初始化的数据。COFF 还引入了符号表，允许链接器识别和解析符号。

    然而，COFF 仍然存在一些局限性，特别是在跨平台支持和扩展性方面。为了克服这些限制，ELF（Executable and Linkable Format）被设计出来，成为现代操作系统中广泛采用的可执行文件格式。ELF 文件格式的设计思路可以总结为以下几点：

    1. 分离节和段的概念：ELF 文件格式区分了节（Section）和段（Segment）。节是链接器使用的基本单位，包含代码、数据、符号表等信息；段是加载器使用的基本单位，描述了如何将文件映射到内存中。通过这种分离，ELF 能够同时满足链接器和加载器的需求。
    2. 灵活的节头表和程序头表：ELF 文件包含节头表（Section Header Table）和程序头表（Program Header Table）。节头表描述了文件中的各个节，包括它们的类型、大小和位置；程序头表描述了文件中的各个段，包括它们在内存中的映射方式。通过这两个表，ELF 文件能够灵活地组织和管理不同类型的数据。
    3. 支持多种架构和平台：ELF 文件格式设计时考虑了跨平台支持，允许不同的处理器架构使用相同的文件格式。这使得 ELF 成为多种操作系统（如 Linux、FreeBSD 等）和处理器架构（如 x86、ARM、RISC-V 等）的通用标准。
    4. 可扩展性：ELF 文件格式设计时考虑了未来的扩展需求，允许添加新的节类型和段类型，而不会破坏现有的结构。这使得 ELF 能够适应不断变化的技术需求。

    通过上述设计思路，ELF 文件格式成功地解决了早期程序文件格式中的许多问题，提供了一个结构化、灵活且可扩展的解决方案，满足了现代操作系统对可执行文件的需求。
