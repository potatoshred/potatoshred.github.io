    RISCV代理内核实验(九)：文件系统

    背景

    Q：现在你有一堆文件，你打算怎么管理它们？

    A：我拉一个map，key是文件名，value是文件地址和文件大小。如何？

    Q：可以，不过，现在你有成千上万个文件，你想寻找去年的某个文件，但是你忘记了准确的文件名，你打算怎么办？或者你从网上下载了一个文件，文件名是火星文，你该怎么办？

    A：我决定把文件按分类存放，比如图片、文档、视频、代码等等，然后再用map存储每个分类下的文件。分类下也会有子分类，比如文档下有工作文档、学习文档、个人文档等等。这样形成了一个树形结构，方便查找，而且解决了命名冲突。树的每个节点用一个数据结构记录该节点的属性，比如节点类型（文件或目录，以及设备）、位置、大小、子节点列表、父节点等。

不过，也不单纯是树形结构，因为有些文件可能会有多个分类标签，比如一个文件既是工作文档又是学习文档，这样就形成了一个有向无环图（DAG）。

    Q:有了目录，文件管理方便了。但文件本身不一定能完全存放在连续的扇区里，你打算怎么解决这个问题？

    A:效仿虚拟内存和分页机制，把文件分成若干个块，每个块存放可以不连续，然后用一个索引表记录每个块的位置。这样就可以实现文件的非连续存储了。另外，需要在节点数据结构中记录文件的块信息。

    Q：用什么数据结构来实现索引表呢？如果是链表的话，虽然磁盘利用率高，但查找效率低；如果是数组的话，查找效率高，但磁盘利用率低。你打算怎么办？

    A：继续效仿虚拟内存和分页机制，使用多级索引结构。但是需要考虑的是，内存页表天然在内存中，而文件系统的索引表需要存放在磁盘上，访问速度较慢。因此，我们使用了一种折中的方法，称为“混合索引”。具体来说，若干指针中，一部分指向直接块（直接存储数据块的地址），一部分指向间接块（存储指向数据块地址的指针），还有一部分指向双重间接块（存储指向间接块地址的指针）。这样可以在保证查找效率的同时，提高磁盘利用率。

    dentry和inode

    到此我们已经有了一个基本的文件系统结构，节点的数据结构包括：

    • 节点名称name
    • 父节点指针parent

    以这两个字段为key，该节点指针为value，可以将所有节点放在一个hash表中，方便查找。

    为了方便文件查找，我们需要尽可能减小结构体的大小。仅需要这两个属性，我们就可以构建一个树形结构。但为了描述文件内容，显然我们还需要更多属性，因此，我们使用指针来引用其他结构体，从而减小主结构体的大小。

    Linux中，这个主结构体是dentry，它包含了文件名、父节点指针、inode指针等; inode结构体包含了文件的元数据，如权限、大小、块索引等。

    • inode结构体指针
      • inum：inode ID
      • type：节点类型（文件、目录、设备等）
      • size：文件大小
      • blocks：文件块数
      • addrs[DIRECT_BLKNUM]：文件块索引（本实验简略采用直接索引，最大支持10个块）

    super_block

    我们是不是忘了什么？

    内存管理中，可分配页框需要用空闲页框链表记录，那么么，磁盘块的分配呢？

    常用空闲块管理策略：

    • 空闲文件目录表：用一个表格记录所有空闲块的位置，分配时从表格中取出一个空闲块，释放时将块位置重新加入表格。
    • 空闲块链表：类似内存页框的空闲链表，使用链表结构记录所有空闲块的位置，分配时从链表头取出一个空闲块，释放时将块位置重新加入链表头。
    • 位图（Bitmap）：使用一个位图来表示磁盘块的使用情况，每个位对应一个磁盘块，0表示空闲，1表示已使用。分配时扫描位图找到第一个0位，释放时将对应位设置为0。

    还记得为什么内存管理中为什么没采用位图吗？因为分配时需线性扫描位图，O(n) 时间复杂度。那么，文件系统中呢？

    A：文件系统中，如 Linux 的 Ext2/3/4中，位图依然是管理磁盘块（Disk Blocks）和 i 节点（Inodes）的主流方案。位图占用空间较小，适合大规模磁盘块管理。在扫描位图寻找空闲块时，操作系统可以利用 CPU 的位运算指令（如 ffs - find first set）一次性处理 64 个甚至更多位，这种“线性扫描”在 CPU 层面其实飞快，大大提升了扫描效率。此外，位图的崩溃恢复相对于链表等结构更简单，减少了文件系统损坏的风险。

    在某些追求高性能的文件系统（如 XFS）中，确实放弃了位图，转而使用 B+ 树（Free Space B+Trees） 来管理空闲空间。这更接近内存管理的思路，因为它能快速定位“足够大”的连续空闲空间。

    Q: 多个硬盘、或硬盘多个分区的情形怎么管理呢？能不能像内存管理那样，统一到一个大的空间里管理？

    A: 理论上是可以的，但实际操作系统中，通常不会这样做。内存是易失性的，断电即空。而硬盘存的是重要档案。如果你把两块硬盘“统一”成一个 D 盘，其中一块坏了，你可能丢失全部数据。此外，内存直接连接在 CPU 的地址总线上，内存并联（双通道）可以显著提升带宽，但硬盘受限于接口和控制器，普通的简单合并并不会让读写速度翻倍。至于硬盘分区，更是为了兼容不同文件系统和操作系统的需求，以及数据隔离和管理方便。

    Q：既然不能合并，那怎么区分一个节点属于哪个硬盘或分区呢？

    A：在节点的数据结构中，增加一个字段，记录该节点所属的硬盘或分区的标识符（如设备号、分区号等）。这样，在访问文件时，可以根据该标识符定位到具体的硬盘或分区，然后进行读写操作。

    在Linux中，super_block结构体用于表示文件系统的超级块，包含了文件系统的元数据，如文件系统类型、单块大小、总块数、空闲块位图、以及设备号、分区号等。每个挂载的文件系统都有一个对应的super_block实例，内核通过它来管理不同的文件系统。

    dentry和inode结构体中也包含了指向所属super_block的指针。dentry 表示路径名条目，需要知道它属于哪个文件系统（哪个挂载点），以便做路径解析、挂载点判断等。inode 在读写、分配块、更新时间、同步等操作时要调用 super_block 提供的函数和配置信息（块大小、块分配策略、超级块标志等）。否则，还得dentry 通过 parent 指针向上找到根，再从根找到 super_block，效率太低。

    为了快速定位inode，类似dentry的hash表，Linux中也有inode的hash表，key是(inum, super_block指针)，value是inode指针。

    为什么dentry的hash表和inode的hash表是分开的呢？

    因为dentry和inode的生命周期不同。dentry是路径名条目，可能会频繁创建和销毁，而inode是物理块的包装，可能会被多个dentry引用。将它们分开管理，可以更灵活地控制缓存和回收策略，提高性能。

    为什么dentry的hash表的key是(父dentry指针, name)，没有包含super_block指针呢？

    因为 dentry 描述的是“路径层级关系”，而超级块描述的是“存储设备边界”，一个是逻辑关系，一个是物理边界。dentry 的查找和路径解析主要依赖于父子关系和名称匹配，而不需要直接考虑存储设备的边界。inode 则需要考虑存储设备的边界，因为它涉及到具体的数据块分配和访问。

    `dentry` 和 `inode` 都包含了指向 `super_block` 的指针，不是重复了吗？

    孤儿 Inode：一个文件被删除但仍被进程打开时，对应的 dentry 可能已经被销毁或断开连接，但 inode 必须依然知道自己的超级块，以便管理剩余的磁盘块和引用计数。

    性能： 在内核代码中，经常只有 inode 指针，如果每次都要先找 dentry 再找 sb（而且一个 inode 可能对应多个 dentry），性能开销太大。属于用空间换时间的典型例子。

    dentry.super_block 和 dentry.inode.super_block 指向的会是不同的 super_block 吗？

    不会.

    device

    本实验简化实现，仅支持单一存储设备，device结构体包含：

    • 设备号dev_id
    • 设备名dev_name
    • 文件系统类型fs_type
    • 文件系统超级块指针*super_block

    file

    虽然dentry和inode可以描述文件的元数据和存储位置，但实际读写文件时，还需要一个file结构体来表示打开的文件句柄。

    为什么？

    同一个文件可能会被多个进程同时打开，每个进程对文件的读写位置、权限等可能不同。如果直接使用dentry或inode，就无法区分不同进程对同一文件的操作状态。file结构体包括：

    • dentry：元数据和存储位置，以供读写操作使用
    • status：文件状态（打开、关闭等）
    • mode：文件访问模式（读、写、读写等）
    • offset：当前读写位置

    “一切皆文件”

    UNIX最具革命性的思想是“一切皆文件”（Everything is a file）。普通文件、目录，甚至打印机、终端等硬件设备，都被抽象为文件，可以通过统一的系统调用接口（如open(), read(), write(), close()）进行访问。这极大地简化了编程模型，增强了系统的可扩展性。

    设备种类是多样的，不同设备的读写操作可能有很大差异，难道要操作系统负责，为每种设备实现一套读写逻辑吗？

    这样显然不现实。设备制造商放不开手脚，操作系统也难以兼容各种设备。所以，还是要把任务化整为零，交给设备驱动程序来完成。操作系统只提供统一的接口和调用机制，具体的读写逻辑由设备驱动实现。

    在inode结构体中，包含了指向文件系统操作函数的指针inode_ops，这些函数由具体的文件系统实现（如ext4、fat32等）提供。这样，操作系统只需调用这些函数指针，而不需要了解具体的实现细节。

    vinode operation

    文件系统操作函数包括：

    文件操作

    函数名 功能描述 返回值
    create 创建文件 新创建的dentry指针
    delete 删除文件 成功或错误码
    open 打开文件 file指针或错误码
    close 关闭文件 成功或错误码
    read 读取文件内容 读取的字节数或错误码
    write 写入文件内容 写入的字节数或错误码
    lseek 设置文件读写位置 新的偏移量或错误码
    link 创建硬链接 成功或错误码
    unlink 删除硬链接 成功或错误码
    … … …

    目录操作

    函数名 功能描述 返回值
    mkdir 创建目录 新创建的dentry指针
    rmdir 删除目录 成功或错误码
    readdir 读取目录内容 目录项列表或错误码
    rename 更改文件名或将文件从一个目录移动到另一个目录 成功或错误码

    回写vinode

    将内存中保存的vinode数据回写到磁盘，该函数一般会在关闭文件时调用。

    钩子函数

    如hook_open、hook_close等，不同于open、close等文件操作函数，这些钩子函数在特定事件发生时被调用。

    例如，在某一文件系统A中，打开文件时需要记录日志，而在文件系统B中又不需要。

    那么，文件系统A自行实现hook_open函数，而文件系统B则不实现该函数（函数指针为NULL）。

    我们可以在open函数中实现文件打开的核心逻辑，而将日志记录的功能放在hook_open中。然后，根据inode_ops中的hook_open指针是否为NULL，决定是否调用该钩子函数。

    最后，将以上函数指针封装在vinode_ops结构体中，并在inode结构体中添加一个指向vinode_ops的指针*inode_ops。这样，不同文件系统可以实现自己的操作函数，并通过inode结构体进行调用。

    mount

    挂载（mount）是将一个文件系统连接到现有的目录树中的过程。通过挂载，可以将不同的存储设备或分区整合到统一的文件系统视图中，用户和应用程序可以通过统一的路径访问不同的文件系统。

    输入：

    • 设备信息
    • 挂载点路径：本实验简化实现，除了挂载为根目录外，仅支持将文件系统挂载到根目录下。

    挂载为根目录

    • 获取device.super_block.root_dentry
      • （该dentry由文件系统初始化时创建，parent指针为NULL，name为”/“）
    • 设置vfs_root_dentry指针为此root_dentry
    • 将此root_dentry加入dentry hash表
    • 将此root_dentry.inode加入inode hash表

    挂载为子目录

    • 获取device.super_block.root_dentry
      • 即挂载点dentry
    • 将root_dentry.name设置为device.dev_name
    • 将此root_dentry的parent指针设置为vfs_root_dentry
    • 将此root_dentry加入dentry hash表
    • 将此root_dentry.inode加入inode hash表
