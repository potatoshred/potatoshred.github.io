    RISCV代理内核实验(八)：实验三：fork、yield、循环轮转调度、wait

    lab3_1 进程创建（fork）

    为了方便进程复制，我们需要在process结构体中记录进程的虚存结构（Virtual Memory Areas, VMA），记录进程的每个虚存区间（如代码段、数据段、堆栈）的起始虚拟地址、大小、类型等信息。

    fork实现

    用户调用fork()时，执行do_usercall()，传入系统调用号SYS_user_fork，然后调用内核中的do_syscall()，根据系统调用号调用sys_user_fork()，sys_user_fork()调用do_fork()实现进程复制。流程如下：

    在do_fork()中，我们遍历父进程的mapped_region数组，根据其类型决定如何操作：

    • CODE_SEGMENT：代码段不会被修改，子进程直接映射到父进程的代码段物理页。

      • 分配相同的页数
      • 复制页内容
      • 登记到子进程的页表
      • 权限：RX

    • DATA_SEGMENT：数据段需要复制，子进程拥有自己的数据段副本。

      • 分配相同的页数
      • 复制页内容
      • 登记到子进程的页表
      • 权限：RW

    • HEAP_SEGMENT：堆段需要复制，子进程拥有自己的堆段副本。需要注意的是，堆可用空间不一定连续，可能存在回收的空间，我们只需要复制实际使用的部分。

      • 寻找实际使用的页
      • 复制页内容
      • 登记到子进程的页表
      • 权限：RW

    • STACK_SEGMENT：栈段需要复制，子进程拥有自己的栈段副本。

      • 分配相同的页数
      • 复制页内容
      • 登记到子进程的页表
      • 权限：RW

    • CONTEXT_SEGMENT：上下文段需要复制，子进程拥有自己的上下文段副本。本实验中，上下文段只包含trapframe，因此我们只需要复制trapframe内容，好在结构体会自动生成拷贝函数。

      • 复制页内容（只需要一页足以容纳trapframe）
      • 登记到子进程的页表
      • 权限：RW

    • SYSTEM_SEGMENT：此段用于映射内核中断向量，一般不需要复制，子进程直接映射到内核中断向量页。

    为什么不是:

    在alloc_process()中，我们实际只初始化了mapped_info数组的前四个元素（STACK_SEGMENT、CONTEXT_SEGMENT、SYSTEM_SEGMENT、HEAP_SEGMENT），而代码段和数据段是动态添加的，毕竟一个进程可能有多个代码段和数据段（如动态库加载）。因此，我们需要使用total_mapped_region来记录当前已经使用的虚存区域数量，并将新的区域添加到数组的末尾。

    lab3_2 进程yield

    这个理解了就很简单，我们只需要在sys_user_yield()中

    • 将当前进程状态设为READY（current->status = READY）
    • 将当前进程加入就绪队列尾部（insert_to_ready_queue(current)）
    • 调用schedule()切换到就绪队列队头的进程运行即可。

    lab3_3 循环轮转调度RR(Round Robin)

    跟yield类似，只不过方式从主动调用变为时钟中断触发。每隔一个TIMER_INTERVAL，触发一次时钟软中断，process.tick_count加一，当process.tick_count达到TIME_SLICE_LEN时，说明当前进程已经运行了一个时间片，需要进行调度切换：

    • 将当前进程状态设为READY（current->status = READY）
    • 将当前进程加入就绪队列尾部（insert_to_ready_queue(current)）
    • 调用schedule()切换到就绪队列队头的进程运行
    • 重置当前进程的tick_count为0。

    lab3_challenge1 进程等待(wait)

    可以看到wait的参数：

    • -1：等待任意子进程结束
    • pid：等待指定pid的子进程结束

    当子进程结束时，调用exit()，将进程状态设为ZOMBIE，此时，出现了两种选择：

    • 立即激活父进程，将其从阻塞状态改为就绪状态，加入就绪队列。
    • 不激活父进程，等待轮转到父进程时再检查该子进程状态。

    目前大多数现代操作系统（如 Linux）更倾向于第一种方案，本实验也是，因为这样可以更快地释放资源，提高系统的响应速度。但是这种方式也会增加一些开销，如果当前 CPU 正在运行其他无关的高优先级任务，频繁地因为子进程退出而触发调度，可能会增加系统的上下文切换负担。方案二则相对简单一些，减少了频繁的调度开销，但可能会导致父进程在等待子进程结束时出现较长的延迟，尤其是在系统负载较高的情况下。

    当父进程调用wait()时：

    • 对于指定pid的子进程
      • pid进程不存在，直接返回-1。
      • pid进程存在，但不是当前进程的子进程，直接返回-1。
      • pid进程存在，且是当前进程的子进程
        • pid进程状态为ZOMBIE，回收资源，状态改为FREE，返回pid。
        • pid进程状态不为ZOMBIE，将当前进程状态设为BLOCKED，调用schedule()切换到其他进程运行。
    • 对于任意子进程
      • 遍历当前进程的子进程列表
        • 无子进程，直接返回-1。
        • 存在ZOMBIE状态的子进程，回收资源，状态改为FREE，返回该子进程的pid。
        • 不存在ZOMBIE状态的子进程，将当前进程状态设为BLOCKED，调用schedule()切换到其他进程运行。
