    RISCV代理内核实验(11)：lab1_challenge2 打印异常代码行

    本实验的关键在与理解elf的.debug_line节的结构。通过该节的信息，打印出异常发生时的代码行号等信息。

    实际上，.debug_line节的解析工作已经做好了，我们只需要调用相关接口即可。跟上一个挑战相比，代码量很少。

    .debug_line节简介

    开发的过程不可能一帆风顺，难免会遇到各种各样的问题。为了定位和解决这些问题，调试器（如gdb）需要知道程序在运行时的状态信息，包括当前执行的代码行号、变量值等。

    运行时，已知的只有指令地址，我们需要哪些信息呢？

    1. 源文件路径
    2. 源文件名
    3. 行号

    至少需要建立几个表？

    1. 指令 -> (fileID, lineNumber)
    2. fileID -> (dirID, fileName)
    3. dirID -> dirPath

    显然，静态表格会有大量重复信息，导致elf文件变大。随着代码量增加，调试信息的大小甚至会超过二进制文件本身！

    哪些信息可以简化呢？比如压缩字段宽度呢？

    还记得差分数组吗？某位老师突发奇想要为某个区间内的成绩增加一个值，为另一个区间内的成绩减少一个值……直接修改数组需要O(n)时间，而使用差分数组，只需要O(1)时间就能完成。

    开发者发现，指令地址（PC）和行号通常是连续且单调递增的。如果不记录绝对值，只记录差值（$\Delta$），不就可以减小数值大小。但仍未解决重复信息的问题，例如数值不变时，仍然需要存储多个相同的差值0。

    自然想到，既然指令地址（PC）和行号通常是连续且单调递增的，那么只在数值变化时，才记录差值（$\Delta$）不就可以了吗？

    为了解决这个问题，.debug_line节使用了一种压缩编码方式，将这些信息压缩存储。


    （The Gistre Blog）

    DWARF 状态机的核心压缩机制

    状态机内部维护一组寄存器，最关键的是：(address, file, line, column)。

    .debug_line 节中存储的是一系列字节码。调试器通过“运行”这些字节码来还原数据：

    标准指令

    OP code 指令 作用
    0x00 DW_LNS_extended_op 扩展指令的前缀
    0x01 DW_LNS_copy 生成一条新的行号信息
    0x02 DW_LNS_advance_pc 增加 address 寄存器的值
    0x03 DW_LNS_advance_line 增加 line 寄存器的值
    0x04 DW_LNS_set_file 设置 file 寄存器的值
    0x05 DW_LNS_set_column 设置 column 寄存器的值
    0x06 DW_LNS_negate_stmt 切换 is_stmt 标志
    0x07 DW_LNS_set_basic_block 设置 basic_block 标志
    0x08 DW_LNS_const_add_pc 增加 address 寄存器的值（使用常量）
    0x09 DW_LNS_fixed_advance_pc 增加 address 寄存器的值（使用固定值）

    特殊指令

    一个字节的指令同时完成“增加地址”、“增加行号”和“向表格中添加一行”三个动作。其利用了代码分布的统计学特性（通常一次跳转几字节，行号变动±几行）。

    .debug_line节的结构比较复杂，具体可以参考DWARF标准第6章。这里不做过多介绍。

    这样，一字节的指令就能大幅压缩数据量。这样做的本质是对变化进行编码，而不是对绝对值进行编码。有没有对变化的变化进行编码呢？专业名词叫做二阶差分编码（second-order differential encoding），二阶差分在极其规律的数据（传感器、音频、等间隔打点）中近乎神技，但在逻辑跳转频繁的代码数据中，二阶差分往往会因为“加速度”频繁变化，反而导致残差比一阶差分更大。

    二阶差分编码之上还有预测编码，如线性预测编码（LPC），在语音压缩（如 FLAC）中大量使用。它不直接记录信号，而是通过前几个点预测当前点。预测公式通常形如：$\hat{x}n = a_1x{n-1} + a_2x_{n-2}$。压缩器只记录残差 (Residual)，即 $x_n - \hat{x}_n$。如果预测得准（即二阶或高阶变化平滑），残差会非常接近 0。早期在带宽极其珍贵的场景，如语音通话中，如果残差足够小，会直接丢弃不传输，造成语音失真，但能大幅节省带宽。本质是过滤了高频。（高频🥲: racist!）

    实验实现

    好在，最麻烦的解压部分已经完成，我们只需要调用相关接口即可。

    在kernel/elf.c::make_addr_line()中，已经实现了解析.debug_line节的功能，并将结果存储在addr_line、code_file等结构体中。

    make_addr_line的调用

    调用按理是件轻松的事，但也有坑。

    按理说，我们要在发生异常时，才调用make_addr_line()，但看了眼make_addr_line()的参数void make_addr_line(elf_ctx *ctx, char *debug_line, uint64 length) ，觉得在加载elf时一起调用更方便一些，不然还得重新构造elf_ctx、解析elf_header，要么还得修改process结构体，存储elf相关信息…

    但偷懒的结果就是，我们的栈空间不够用了。

    如果在加载elf时调用make_addr_line()，占用的是机器态分配的4096B栈空间，而我们的make_addr_line()又需要整个.debug_line节的内容，而且解析后的数据也要存储在内存中，栈空间显然不够，就会发生make_addr_line时卡住、指令访问故障等现象。

    好在修改栈大小不难，只需要将kernel/machine/*内的所有4096改为8192或更高即可。

    实验指导书上也给了另一种思路：把debug_line拷贝到程序所有需映射的段数据之后，例如0x82000000。
