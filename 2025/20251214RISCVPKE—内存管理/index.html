    RISCV代理内核实验(五)：内存管理

    在本实验中，我们将实现RISCV代理内核的内存管理功能，包括页表管理、虚拟内存映射和内存分配等。

    “All problems in computer science can be solved by another level of indirection.”
    “计算机科学中的所有问题都可以通过引入一个中间层（间接层）来解决。”
    — David Wheeler

    背景

    实验一中，我们成功加载ELF文件并跳转到用户态执行，实现了单进程的内存分配。

    但是，我们是直接使用物理地址来访问内存的。还记得我们怎么分配的内存吗？

    [0x8000_0000 - 0x8100_0000]这段内存划分给了Smode，

    [0x8100_0000 - 0x8800_0000]这段内存划分给了Umode。

    我们还要给每个进程分配kstack和ustack，保证每个进程有独立的用户栈和内核栈（用于处理异常）。

    单进程的情况下，这样的内存分配是可以的，但是多来几个进程又该怎么办呢？

    看看历史上是怎么办的。

    最早有人想，我事先将内存划分成几个区域，每个区域都有独立的内核栈和用户栈，分配给不同的进程使用。这样不就行了？但是，每块区域的大小该怎么定呢？如果定得太大，内存浪费，能分的区域数量就少；如果定得太小，进程运行时可能会栈溢出。为了防止自己写的程序栈溢出，用户还要事先知道用户栈的大小。这中间就会产生沟通成本，还需要用户耗费脑力去避免栈溢出。显然，这种方式并不理想。

    理想的情况是什么？我们从用户的角度来看：

    1. 我的空间是无限的，我可能不会用，但我要用时就得有。
    2. 我的进程有独立的空间，隐私安全。
    3. 我不需要关心别人，我的栈的地址永远是连续的，想用什么用什么。

    显然，作为乙方的你，觉得甲方的要求很过分，内存又不是无限的，怎么可能满足他的要求呢？就像服务业一样，用户只需要关心自己的需求，服务商负责提供服务，用户不需要关心服务商的资源分配和管理。交给服务商去想办法吧。

    有人想了个办法，既然静态分区不行，那就动态分配吧。用户需要多少内存，就在空闲内存中找一块合适的分配给用户。这段时期，首次适应、最佳适应等算法被提出，但都不能很好地解决内存碎片问题：分配时确实找到了合适的内存块，但释放时却产生了碎片，尽管总空闲内存可能足够，但无法满足新进程对连续内存空间的需求。

    有人提出改进：先将整个进程的数据暂存到磁盘，再重新分配一块连续的内存空间，然后将数据从磁盘重新读回内存，但这个过程涉及大量磁盘I/O，效率很低。

    问题的根源在于，用户进程还是需要连续的物理内存空间。

    划时代的想法出现了：内存切片。跟前面的静态分区相似，但把内存划分成更小的块，称为页（page），就像切西瓜，先给每个人切一块，要是还想吃，就再切一块。从“刻舟求剑”到“量体裁衣”，从“雕版印刷”到“活字印刷”，不断满足进程的不确定性和突发性的需求特征，解放了用户的生产力。

    静态分区在确定性环境下效率极高，但面对变化时显得僵化；分页管理增加了管理开销，但适应性强，能应对多样化需求。没有放之四海而皆准的管理方法，只有最适合特定情境的管理策略，在确定与不确定之间寻找动态平衡。

    分页机制之上，又更进一步，提出了虚拟内存的概念。用户进程不再直接使用物理地址，而是使用虚拟地址。操作系统负责将虚拟地址映射到物理地址，这样用户进程就可以认为自己拥有连续的内存空间，而实际上这些空间可能分散在物理内存的各个角落，甚至部分数据还存储在磁盘上。

    本质是 “逻辑视图”与“物理视图”的解耦。

    PMM: 物理内存管理

    分页从哪个阶段开始呢？

    分页的目的是满足多进程的内存需求，因此分页管理从多进程开始之前就要启动，也就是在S态内核初始化阶段。

    M态肯定不需要分页管理，M态的任务比较简单，也不需要频繁切换进程，因此直接使用物理地址即可。

    S态内核初始化阶段，我们需要初始化物理内存管理模块（Physical Memory Management，PMM）。PMM的职责有：

    1. 管理物理内存的分配和释放。
    2. 提供页框（page frame）的分配接口，页框是分页管理的基本单位，通常为4KB。
    3. 维护空闲页框链表，方便快速分配和回收。

    简单来说，要做的只有两件事：页框分配和页框回收。

    • 分配：从空闲页框集合中取出一个页框，返回其物理地址。

      • 分配的页框不能是已经被使用的页框
      • 分配的页框不能是保留页框（比如内核代码区、数据区等）

    • 回收：将页框重新加入空闲页框集合。

      • 回收的页框必须是已经被分配出去的页框

    空闲页框集合用什么数据结构来表示呢？

    看看历史的选择吧：

    • 位图（bitmap）：每一位表示一个页框的状态，0表示空闲，1表示已分配。
      • 优点：空间效率高，4GB内存只需 128KB 位图。
      • 缺点: 分配时需线性扫描，O(n) 时间复杂度
      • 代表系统：早期批处理系统、CTSS、Multics
    • 空闲链表：将空闲页框通过链表连接起来，分配时从链表头取出一个页框，回收时将页框插入链表头。
      • 优点：分配和回收操作时间复杂度为O(1)。利用空闲页框本身存储链表指针 (无额外开销)。
      • 缺点：无法快速分配连续多页
      • 代表系统：Unix V6/V7, BSD 4.x, 本实验 riscv-pke
    • 伙伴系统（Buddy System）：将内存划分为大小为2的幂次方的块，分配时找到最合适的块，回收时合并相邻的空闲块。本质上是一种分层的空闲链表。
      • 优点：减少内存碎片，支持快速分配连续多页
      • 缺点：实现复杂，管理开销较大
      • 代表系统：Linux (1991年至今), Windows NT
    • ……….

    riscv-pke使用的是最简单的 空闲链表 结构，适合教学目的，体现了物理内存管理的核心思想。 xv6也采用了类似的方式。

    VMM: 虚拟内存管理

    现在，请你忘掉物理内存的概念，你只知道需要的时候，直接向操作系统申请alloc_page()就好了。

    虚拟内存的核心在于地址映射。每个进程都有自己的虚拟地址空间，操作系统通过页表将虚拟地址映射到物理地址。

    satp（Supervisor Address Translation and Protection，监管者地址转换和保护）是S态下的一个CSR。satp 有三个域：

    • MODE：地址转换模式，RISCV64中通常为8，表示启用SV39分页机制。
    • ASID：地址空间标识符，用于区分不同进程的地址空间。
    • PPN：页表的物理页号，指向当前进程的根页表。

    通常，第一次进入S态时，会设置satp=0以禁用分页，在S态初始化页表以后，更改satp值来启用分页。

    本实验采用Sv39分页机制，虚拟地址空间为39位，分为三级页表，每级页表包含512个页表项（PTE），每个页表项大小为64bit，所以每个页表占用4KB（512 * 8 bytes），正好一个页框的大小。

    RV64下，satp寄存器的PPN字段占44位，表示页表的物理页号。页表的物理地址可以通过PPN << 12计算得到(页框大小为4KB=2^12B)。

    44+12=56位，为什么不是64位？

    正好缺了8位，这是因为按字节寻址，

    吗？

    并不是。还记得反汇编指令时，虚拟地址是什么样的吗？比如8100015a: 04200513 li a0,66，地址结尾并不是0x00。

    实际上，56位物理地址可以寻址 $2^{56}$ 字节的内存，相当于64PB。在可预见的未来，对于绝大多数应用（包括大型服务器和数据中心）都是完全足够的。直接实现完整的64位物理地址（16EB）需要更复杂的硬件电路来处理更多的地址线，会显著增加成本、功耗和设计复杂度，但收益却很小。

    x86-64/AMD64支持52位物理地址，寻址4PB内存空间。

    ARMv8支持48位物理地址，寻址256TB内存空间。

    ARMv9支持52位物理地址，寻址4PB内存空间。(2024年手机开始搭载基于Armv9架构的芯片)。

    开始之前，请一定要弄清楚以下概念之间的关系：

    • VA
    • PA
    • Page
    • Page Table
    • Page Directory
    • PTE
    • PDE
    • VPN2, VPN1, VPN0

    512叉树，根节点是PD。完全512叉树可登记512 * 512 * 512 * 4KB = 512GB的内存空间。根据虚拟地址的实际使用情况，激活对应的节点。

    咦？不是说44位PPN可以寻址64PB吗？为甚么这里只能登记512GB？

    Sv39只使用了39位虚拟地址，能表示的最大地址空间确实是2^39 = 512GB。实际可用的虚拟地址空间仅限于512GB。我们还要弄清：

    PD只有一个吗？

    不是。每个进程都有自己的页表（包括PD、PMD、PT），包括内核进程也是如此。实际上，进程的PCB中会保存当前进程的satp值，以便在进程切换时加载对应的页表。

    这么多PD，会发生页框冲突吗？

    冲突避免是由PMM模块负责的。不过，不同进程有时也会共享某些物理页框，比如fork出来的子进程会共享父进程的代码段页框。

    内核进程为什么也有自己的页表？内核进程不是访问物理内存吗？

    现代CPU中为了加速地址转换以及检验访问权限，有单独的硬件模块MMU（Memory Management Unit，内存管理单元）负责。CPU 发出的每一条访存指令，地址都会被 MMU 拦截并进行查表翻译，并不会区分“现在是内核在跑”还是“现在是用户在跑”。前面也提到，在S态初始化页表以后，更改satp值来启用分页。如果要让内核使用物理地址，就必须在每次陷入内核（系统调用/中断）时关闭 MMU，退出时再打开。这在性能上是灾难性的，因为关闭/开启 MMU 会清空流水线和TLB缓存。

    另一方面，内核进程也会出现“多进程”，比如同时发生多个中断处理程序。又比如，多核CPU中，每个核上都运行着内核进程，这些内核进程之间也需要隔离。

    最后，更需要指出的是，页表不仅仅用于地址翻译，还包含权限位（R/W/X）。通过页表，可以将内核代码段设为“只读”。如果低调的黑客试图用野指针修改代码段，CPU 会触发异常，防止系统彻底崩溃或被篡改。早期DOS系统采用实模式没有页表，内核代码段缺乏保护，你甚至可以修改键盘中断向量来修改按键，比如说按下S键输出B。

    内核进程页表

    实际上，在内核进程的页表创建前，我们已经在使用内存了。毕竟，没有内核代码，又怎么创建页表呢？但在用户态进程运行前，我们必须创建内核进程的页表，分配号页框，并将内核代码段、数据段映射进去，才能让用户态进程正常运行。

    所以我们要做的是给内核补票。

    仔细回想，在pmm阶段，我们刚刚初始化了空闲页框链表g_free_mem_list，那么，

    第一个被分配出去的页框用来做什么呢？

    是的，正是作为内核进程的顶级页表PD。

    内核进程的页表要登记哪些区域呢？

    对本实验来说看，将

    [KERNEL_BASE, KERNEL_BASE + PKE_MAX_ALLOWABLE_RAM)

    ↕ 映射为

    [DRAM_BASE, DRAM_BASE + PKE_MAX_ALLOWABLE_RAM)

    显然，PKE_MAX_ALLOWABLE_RAM不会超过2^39。

    这段区域分成两段：

    • 内核代码段：

      • 虚拟地址：[KERNEL_BASE, KERNEL_BASE + text_size)
      • 物理地址：[DRAM_BASE, DRAM_BASE + text_size)
      • 权限：RWX=101，只读且可执行，不可写

    • 内核数据段+堆+栈+剩余内存：

      • 虚拟地址：[KERNEL_BASE + text_size, KERNEL_BASE + PKE_MAX_ALLOWABLE_RAM)
      • 物理地址：[DRAM_BASE + text_size, DRAM_BASE + PKE_MAX_ALLOWABLE_RAM)
      • 权限：RWX=110，可读可写，不可执行

      不对呀，你把所有RAM都映射进去了，我用户进程还能用啥？

    内核进程是所有用户进程的监护人，监护人需要随时访问用户进程的内存空间，因此需要映射所有物理内存。

    内存都设成了不可执行，我用户进程代码咋跑吗？

    内核进程页表只负责内核态的地址转换和访问控制，用户态的地址转换和访问控制由用户进程自己的页表负责。具体来说，用户进程运行时，satp会被切换为用户进程的PD，自然会按照用户进程页表中的权限来访问内存。而且，PTE中的U位会被设置为1，表示用户态。

    那用户进程页表会把内核代码段映射进去吗？

    不会。用户进程页表只会映射alloc_page()分配的页框，自然不会包括内核代码段所在的页框。

    内核不能跑一跑用户进程的代码段吗？

    内核代码注入了解一下。W^X（Write XOR Execute）原则要求内存页要么可写，要么可执行，但不能同时具备这两种权限。这样可以防止恶意代码注入攻击，提高系统安全性。

    👶进程会有叛逆期吗？会需要自己的隐私吗？

    用户进程页表

    pmm和vmm模块初始化完成后，我们就可以enable分页，并切换到用户态运行用户进程了。

    用户进程怎么创建呢？

    思路1：直接创建

    思路2：现代Linux风格的fork + exec创建

    思路2是什么说法？

    fork一开始是为多核并行处理设计的。假设有两个CPU核，核A运行进程A，核B运行进程B。现在核A想创建一个新进程C，并让核B运行它。最简单的方式是，核A创建进程C的PCB和页表，然后将进程C的PCB放入就绪队列，等待核B调度运行。

    UNIX初期，系统仅有两个固定的 shell 进程，例如：终端用户输入ls命令后，该终端对应的shell进程会自己执行磁盘I/O操作，将ls程序的代码和数据从磁盘载入内存，直接覆盖掉自己所在的代码区域。ls命令运行完毕后，其退出逻辑会再次执行磁盘I/O，将shell程序的代码重新载入内存，恢复shell界面。

    是的，这个时期还没有虚拟内存，内存管理非常原始，所有进程共享同一块物理内存区域。

    这是exec的雏形，但新程序直接覆盖当前shell进程的内存空间。Shell进程被覆盖销毁，执行完命令需重新加载。频繁磁盘I/O导致系统响应缓慢，更难受的是Shell状态无法保持，无法实现复杂交互，比如管道、重定向等。

    很自然有人想到Save-Load：将shell进程暂时交换到磁盘上保存起来。

    听起来是不是很熟悉？没错，这就是swap的思想源头。现代swap机制将交换的粒度从整个进程细化到内存页，并与虚拟内存技术深度融合，成为现代操作系统内存管理的基石 。

    为此，需要先复制一个shell进程的副本，然后让命令程序去覆盖这个副本进程。这个“复制当前进程”的操作，就是系统调用 fork的核心思想。

    fork的核心理念——复制当前进程——被引入，但其初始目的非常单纯：为 exec准备一个“牺牲品”进程。

    但是，频繁的I/O操作依然是个大问题。

    那就想办法减少I/O操作吧。

    有人观察到：子进程不一定会完全覆盖父进程的内存空间，这部分区域并不需要Save-Load。

    有人提出了写时复制（Copy-On-Write，COW）技术：fork时不立即复制整个进程的内存空间，而是先共享父进程的内存页，并将这些页标记为只读。当子进程或父进程尝试写入这些共享页时，才触发页错误异常，操作系统捕获该异常后，才为该页分配一个新的物理页，并将数据复制过去，然后更新页表，将该页标记为可写。这样，大大减少了不必要的内存复制和I/O操作，提高了系统性能。

    这样做会错用父进程的数据吗？
    • 代码段和数据段：如果两个进程不同，代码段和数据段自然不同，那么在加载ELF文件时就会执行写操作，触发COW机制。
    • 堆和栈：堆和栈一开始是空的，只有在进程运行时才会写入数据，触发COW机制。

    当然，防君子不防小人，如果恶意进程试图通过野指针访问父进程的数据，早期Unix系统是无法防范的。这个任务要交给上述的后来的内存保护机制去解决了。

    就这样，从“交换”到“复制”，再到“写时复制”，内存管理技术不断演进。虽然现在内存已经足够大，更有虚拟内存技术，但fork + exec的设计理念依然被现代操作系统广泛采用，因为它高效且灵活，能够满足多样化的进程创建需求。

    虚拟内存下的ELF加载

    实验一Bare模式下，我们在kernel.lds中将内核代码段和数据段规划在0x8000_0000 - 0x8100_0000这段内存中，而在user.lds中将用户进程的代码段和数据段规划到0x8100_0000 - 0x8800_0000这段内存中。这样，我们可以很方便的直接将用户进程的代码段和数据段加载到物理内存中对应的地址，然后跳转到入口开始执行用户进程。

    在启用虚拟内存后，我们就不需要再使用user.lds。ELF加载显然在S态内核中完成，但在加载ELF之前，我们需要：

    1. 创建用户进程的页表PD。

    2. 分配页框，用于用户进程的trapframe。

    3. 分配页框，用于用户进程的内核栈。

    4. 分配页框，用于用户进程的用户栈。

      2、3、4需要登记到进程PD吗？

    用户栈登记到进程PD容易理解，申请了什么材料得登记在案嘛，而且还要设置U位和R/W位。

    内核栈只在把kernel_sp从 trapframe 取出后才被实际使用，当 CPU 真正开始往内核栈压栈或读写数据时，页表已经切换到内核页表了。从安全角度看，用户页表不映射内核栈可以防止用户态恶意代码攻击内核数据。

    trapframe呢？

    这个问题的关键是：

    用户进程需要访问`trapframe`吗？

    回想一下trapframe的作用：保存用户进程从用户态切换到内核态时的寄存器状态，以便在返回用户态时恢复。字段包括通用寄存器、程序计数器（PC）、中断处理程序的栈指针，以及本实验中新增的kernel_satp寄存器等。

    用户进程本身似乎并不需要直接访问trapframe。

    但仔细想想，trap时，satp何时切换的？

    保存现场时，内核会将当前satp写为trapframe中暂存的kernel_satp值，。那么，trap触发后，satp切换前，

    页表是谁的？

    satp还没切换回来，自然还是用户进程的页表。也就是说，这个窗口期内，虽然CPU 已经处于 S-Mode，但环境（页表）还是旧的用户环境。

    这个窗口期内，我们需要访问trapframe中的satp值以及kernel_sp等，那么，trapframe 的虚拟地址必须在用户页表中有效。否则，保存寄存器的指令会触发缺页异常（Page Fault），

    那我换个思路，把 trapframe 内容登记在内核页表里呢？先切换 satp 到内核页表，再保存到trapframe寄存器不就行了？

    让我们理一理：

    • 切换页表需要修改 satp 寄存器。
    • 修改 satp 需要先从某个地方读出旧的 kernel_satp 值。这个地址存在哪？通常存在 trapframe 结构体的某个字段里。
    • 读trapframe，要用到sscratch寄存器。在进入用户态前，sscratch保存了用户进程的trapframe的地址。
    • 先用 csrrw a0, sscratch, a0 将 sscratch 的值读到 a0 寄存器中（并将 a0 的值暂存到 sscratch 中，以免破坏现场），这样 a0 就是 trapframe 的地址。
    • 然后用 lw t0, offset(a0) 读出 trapframe 中的 satp 值到 t0 寄存器中。
      • 那么，用户程序原来在 t0 里的数据就永久丢失了，破坏了现场。
      • 不可行。
    • lw a0, offset(a0) 不就行了？
      • 这样做会破坏 a0 寄存器的值，用户进程的trapframe丢了…
      • 不可行。

    那我不存到trapframe里，把satp值存在内核空间某个固定的内存地址呢？

    仔细一想，又是个蛋生鸡的问题：

    1. 假设把satp 的值存在 0x80001000 处。
    2. CPU 运行在用户态，satp 指向用户页表。
    3. Trap 发生了，你想去读 0x80001000处的satp 值切换页表。
    4. 不对呀，0x80001000不在我的用户页表里啊！

    所以，trapframe 还是得登记在用户页表里。

    问题终于想通了。我们终于可以加载ELF文件了。🥲

    好在剩下的都是简单的了。

    • 根据PT_LOAD段的信息，alloc_page()分配页框
    • 将段内容加载到页框中
    • 将这些页框登记到用户进程的页表PD中
    • 设置合适的权限位（R/W/X/U）
